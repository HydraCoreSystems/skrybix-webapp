# Skrybix

Skrybix is Gathering Moss's plant inventory and label-printing application.
It remains the authority for mother-plant and cutting identities.

## GM Commerce handoff

> **Status note:** the commerce SKU standardization described below is
> implemented, committed, and open as a draft PR
> (`claude/commerce-sku-implementation`, PR #11) — **not yet merged or
> deployed**. Production Skrybix still runs the pre-standardization
> behavior where `sku === sourceRecordId`. This section documents the
> contract PR #11 will introduce once merged; see
> `docs/Skrybix_Commerce_SKU_Design_Report.md` for the full design,
> verification, and deployment-order record.

Skrybix remains the source of truth for cutting **and mother plant**
identity — `cutting_id`/`mother_id` never change, are never renamed, and
are never repurposed as a commerce identifier. In **Cuttings** or **Mother
Plants**, a human checks **Select for GM Commerce** beside an existing
record, additionally choosing a genus/plant registry code (and, for a
mother, required sale facts — see below). This persists
`commerce_selected_at` on the original source record **and** atomically
assigns a separate, standardized, immutable **commerce SKU** — a wholly
different value from `sourceRecordId`, never generated by copying it.

**`sourceRecordId` and `sku` are two different, independently meaningful
fields — do not assume they are ever equal, and never derive one from the
other.** `sourceRecordId` is the permanent Skrybix `cutting_id`/`mother_id`,
used for idempotent import and for the acknowledgement call. `sku` is the
new standardized identifier, in the form `{GENUS}-{PLANT}-{MOTHER}[-C{CUTTING}]`
(e.g. `HY-KRQ-01`, `HY-KRQ-01-C01`) — never equal to `sourceRecordId` by
construction, immutable once assigned (the database itself rejects any
`UPDATE` or `DELETE` against an assigned SKU mapping).

**`sourceRecordId` is not guaranteed unique across record types on its
own.** `cutting_id` and `mother_id` are each only unique within their own
Skrybix table, not against each other — nothing in the schema prevents a
mother and a cutting from someday sharing the same raw ID string. GM
Commerce's own idempotent-import key must therefore be the **composite**
`(plantRecordType, sourceRecordId)`, not `sourceRecordId` alone. The
acknowledgement endpoint (see the table below) accepts an explicit type
discriminator for exactly this reason.

A mother plant record has no `parentSourceRecordId` (it has no parent in
Skrybix's own hierarchy, unlike a cutting) and no `archivedAt` (mother plants
have no archive concept in this schema, only real deletion — `archivedAt` is
always `null` for a mother record). A mother record additionally carries a
required `motherFacts` payload (condition, pot/plant size, shipping
presentation, rooted/established status, sale-photo subject) that a cutting
record never has (`motherFacts: null` on every cutting record, always).
**GM Commerce must use `motherFacts` for established-whole-plant listing
content — not cutting-style language — whenever `plantRecordType === "mother"`.**

### Access and setup

Apply the updated `supabase/schema.sql` to add the durable selection and
acknowledgement columns (on both `cuttings` and `mother_plants`). Set a
non-empty `COMMERCE_EXPORT_KEY` in the Skrybix deployment environment, using
a unique random value such as:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Do not commit the key. GM Commerce sends it on every request:

```http
Authorization: Bearer <COMMERCE_EXPORT_KEY>
```

The API route is intentionally excluded from Skrybix's browser-session
middleware so GM Commerce can use this bearer credential. The route itself
fails closed with `401` unless the configured token exactly matches; it does
not provide Supabase access, browser-session access, or source-record write
access to GM Commerce other than the documented acknowledgement timestamp.

| Operation | Endpoint | Result |
| --- | --- | --- |
| Read pending selections | `GET /api/commerce/v1/plants` | Returns only human-selected, unacknowledged records — both cutting and mother plant records, mixed in one list distinguished by `plantRecordType`. Every returned record already has a real, non-null `sku` and (for mothers) a real `motherFacts` — the export fails closed rather than ever sending a placeholder. |
| Acknowledge an imported record | `POST /api/commerce/v1/plants/:recordId/acknowledge` | Durably marks that selected source record acknowledged, whichever type it is. Accepts an optional `plantRecordType` (`"cutting"` \| `"mother"`) as a query parameter or JSON body field — when supplied, addresses that table only; **send it** once your import records `plantRecordType` alongside `sourceRecordId`, since it's the only way to reach a record whose ID collides with the other type's. Omitting it falls back to a "try cutting, then mother" heuristic kept only for compatibility, which is not collision-safe. Repeating an acknowledge call is safe either way. |

```json
{
  "exportVersion": "1.0",
  "sourceSystem": "skrybix",
  "retrievedAt": "2026-08-01T00:00:00.000Z",
  "records": [
    {
      "sourceSystem": "skrybix",
      "sourceRecordId": "HY-ABC01-C01",
      "sku": "HY-ABC-01-C01",
      "displayName": "Hoya example",
      "parentSourceRecordId": "HY-ABC01",
      "plantRecordType": "cutting",
      "state": "active",
      "selectionState": "selected",
      "selectedAt": "2026-08-01T00:00:00.000Z",
      "acknowledgedAt": null,
      "archivedAt": null,
      "sourceCreatedAt": "2026-08-01T00:00:00.000Z",
      "motherFacts": null
    },
    {
      "sourceSystem": "skrybix",
      "sourceRecordId": "HY-XYZ01",
      "sku": "HY-XYZ-01",
      "displayName": "Hoya whole-mother example",
      "parentSourceRecordId": null,
      "plantRecordType": "mother",
      "state": "active",
      "selectionState": "selected",
      "selectedAt": "2026-08-13T00:00:00.000Z",
      "acknowledgedAt": null,
      "archivedAt": null,
      "sourceCreatedAt": "2026-06-01T00:00:00.000Z",
      "motherFacts": {
        "photoSubject": "exact_plant",
        "potSize": "6in nursery pot",
        "plantSize": "18in vine",
        "rootedEstablished": true,
        "shippingPresentation": "ships_in_pot",
        "shippingPresentationDetail": null,
        "conditionNotes": "Recently cut back for shipping"
      }
    }
  ]
}
```

Note `sourceRecordId: "HY-ABC01-C01"` vs `sku: "HY-ABC-01-C01"` above — deliberately different values, not a typo. See `docs/Skrybix_Commerce_SKU_Design_Report.md` §7 for the full `motherFacts` field reference.

`state` truthfully reports the current source lifecycle: `active`, `sold`, or
`archived` (a mother record's `state` can only ever be `active` or `sold` —
see the `archivedAt` note above). It is not marketplace availability or
inventory quantity. `displayName` is the stored source display name, not a
generated listing title. The source has no `updated_at`, listing-readiness
field, price, quantity, photo folder, or marketplace data, so none is
inferred.

GM Commerce must import idempotently on `sourceSystem` plus the **composite**
`(plantRecordType, sourceRecordId)` — `sourceRecordId` alone is not
guaranteed unique across record types (see above) — persist `sku` exactly as
received, and call the acknowledgement route (with the `plantRecordType`
discriminator) after its own durable intake succeeds. An acknowledged record
remains visibly acknowledged in Skrybix but is no longer returned by the
pending-selection response. There is no callback, two-way synchronization,
or GM Commerce write access beyond that narrow acknowledgement timestamp;
GM Commerce owns all downstream commerce state.
